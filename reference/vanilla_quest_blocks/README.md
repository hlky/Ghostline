# Vanilla Quest Building-Block Corpus

This directory is a deliberately small extraction of vanilla questphase
resources used to research reusable Ghostline quest blocks. The CR2W files in
`cr2w/` are untouched game resources; `raw/` contains their WolvenKit JSON
serialization for structural inspection.

These files are references, not templates that may be copied blindly. Vanilla
phases depend on quest-local facts, communities, NodeRefs, workspots, vehicles,
devices, journal paths, and nested phase resources. A Ghostline block becomes
runtime-ready only after its reduced template has been isolated, its bindings
are explicit, it round-trips through WolvenKit, and it passes an in-game test.

## Reduced Ghostline templates

The minimal Ghostline-owned candidates are generated by
`tools/generate_quest_block_templates.py` and
`tools/generate_ai_vehicle_block_templates.py`, with the advanced templates
generated by `tools/generate_advanced_quest_block_templates.py`, under
`source/raw/mod/ghostline/quest_blocks/templates`. They use exact
`{{placeholder}}` scalar values for the compiler's replacement contract and
have passed JSON handle validation plus a WolvenKit 8.17.4
deserialize/serialize round trip.

The limitations are intentional and should remain visible:

- `combat_encounter` currently represents only `already_hostile` +
  `all_defeated`, but it does accept a variable-size named entry list.
  Suspicion/escalation behavior and mixed friendly/hostile communities still
  require a broader block.
- `investigate_clues` accepts a variable-size clue list and requires all
  listed clues. `required_count < clue count` still requires a custom phase.
- `optional_condition` is a converging entry-time fact test. It does not claim
  to implement the schema's `continuous` evaluation.
- `choice_gate` is exactly two fact-backed branches. Phone choices and scene
  exits already have their own runtime systems and should not be represented
  by merely renaming these fact conditions.
- `escort_npc` is exactly three ordered trigger gates and applies gameplay AI.
  It does not synthesize patrol splines, teleport
  recovery, combat interruption, or companion cleanup. Those remain
  world/community or scene-owned behavior.
- `carry_npc` completes when the carried NPC reaches the destination while
  still mounted to V. It does not yet require a subsequent body drop,
  trunk-placement event, or target cleanup.
- `deliver_vehicle` accepts a single vehicle NodeRef and a single destination
  trigger. It does not handle vehicle spawning, ownership, damage/failure,
  exit/unmount requirements, or post-delivery despawn.

### Readable shard progression

Vanilla evidence does not support treating the pickup-notification preview as
a quest-readable event. The extracted phases for `ma_wat_lch_03`,
`ma_wat_lch_05`, and `ma_wat_lch_15` all correspond to journal objectives
named `read_shard`, but none contains
`questJournalEntryVisited_ConditionType`. They advance from inventory, loot, or
interaction state instead. Ghostline's generated `read_shard` block therefore
uses readable-item ownership as its completion condition and leaves opening
the shard as presentation.

Computer pages and emails are a distinct device/UI flow. They can advance
quests when opened, but that does not establish that an inventory shard's
pickup-preview overlay emits the same event. A reusable terminal-document
block should be isolated from a vanilla computer quest rather than folding
that behavior into `read_shard`.

That isolation now exists in `sq021_randys_room`. Its computer graph activates
the target journal internet page, routes the page-selection output into a
quest fact (`sq021_thisisfucked_read`), and waits for that fact in the phase.
The completion signal therefore belongs to the authored computer UI graph; it
is not a generic `questJournalEntryVisited_ConditionType`. A Ghostline block
must bind a computer, a document entry, and a dedicated completion fact.

### Delayed contact progression

The `sq011` references use `questGameTimeDelay_ConditionType` for delays of
23 hours, three days, and five hours. The timer is only the gate. Phone calls,
messages, journal activation, and content-token waits remain explicit
downstream nodes and should be represented as separate blocks or orchestration
steps. This keeps `time_gate` deterministic and prevents it from implicitly
owning contact presentation.

### Continuous stealth monitoring

`sts_wbr_jpn_03_streetstory` keeps a stealth objective active while a parallel
branch waits on `jpn_03_stealth_fail`. The failure branch changes the journal
state and later selects the non-stealth debrief; the successful path preserves
the stealth outcome. This is materially different from the existing
`optional_condition` reduced template, which evaluates one fact only when
entered. A reusable `stealth_monitor` needs a lifecycle (start, fail signal,
stop/converge) and must run alongside the main objective flow.

See [EXTRACTION-NOTES.md](EXTRACTION-NOTES.md) for exact nodes, proposed typed
contracts, and isolation boundaries.

Do not call these templates runtime-proven until an instantiated child
phase has been packed, installed, and exercised in game. A successful CR2W
round trip proves serialization and handle topology, not engine behavior.
