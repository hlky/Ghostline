# Candidate building blocks from mq003 and mq010

These are **proposed reductions**, backed by the two [quest dossiers](README.md).
No new compiler stage types or serialized donor templates were implemented.
The names below describe contracts; they are not a promise that the current
quest schema accepts those names.

The useful split is between small primitives (condition, fact, journal change),
lifecycles (meeting, investigation, encounter), and compositions (access routes,
optional evidence affecting a later report). Keep the author-facing composition
readable while retaining its dependencies and exit policy underneath.

## Existing Ghostline overlap

Current implementation was checked in `tools/quest_compiler.py`, particularly
`build_time_gate_phase`, `build_investigate_clues_phase` and
`build_combat_encounter_phase`, alongside `tools/quest-schema-v1.json` and the
[isolated donor corpus](../../../../reference/vanilla_quest_blocks/README.md).

| Existing surface | What these quests add |
| --- | --- |
| Direct `time_gate` | Already implements elapsed game time, with optional completion fact. mq010 composes it with objective state, spatial return and scene cancellation; these should stay separate responsibilities |
| Direct `investigate_clues` | Current builder uses **ordered `Started` scans**. mq003 uses parallel **`Finished` scans**, scene-reaction outputs, AND join and direct-discovery bypass. This is a real behavioral gap |
| Direct `combat_encounter` | Current builder activates a community, waits spawn, injects threats for named entries and waits community defeat. mq003 adds vehicle arrivals, mount/unmount readiness, per-entry journal counters and abandonment |
| `interact_device`, `acquire_item`, journal/fact primitives | Useful components, but a scene choice, a device state transition, ownership and actual reading remain different signals |
| Scene exit contracts and `phase_template` | Existing schema/compiler surfaces can carry custom resource contracts. The research argues for stronger validation and composition rather than another generic fact gate |
| Existing meeting/native lifecycle tooling | Reuse its readiness, named outcomes and cleanup ownership; mq010 adds ambient-to-player handoff and knowledge-dependent consequence |

## 1. Scene call with a checked interface

**Purpose:** invoke one named scene entry and handle declared notifications,
outcomes and side channels.

- Inputs: scene resource, marker, entry name, actor/world bindings,
  interruption/return policy, output-to-effect mappings.
- Outputs: named progression outcome, optional nonterminating notifications,
  interruption/cancellation and presentation side channels.
- Ownership: caller owns durable progression effects unless the explicit
  contract declares scene-owned fact/journal effects. Acknowledge both styles
  in vanilla; do not assume all scene effects live in phases.
- Evidence: mq003 homeless scene has ten entries/twelve exits; mq010 Barry
  scene exposes `barry_tier` and `door_locked_out` independently of `End 0`.
- Validation: entry/exit exists; selected output is wired; mapping honors
  termination semantics; each actor is acquired; cancellation retires listeners.

**Acceptance:** complete, leave, interrupt, return, and cancel from every entry;
verify a side-channel output cannot accidentally complete the objective.

## 2. Staged meeting with ambient handoff

**Purpose:** make a world encounter available before entering player dialogue.

- Inputs: community/entries/phase, readiness conditions, offscreen setup gate,
  ambient scene entry, player scene entry, engagement conditions, content scope.
- Outputs: meeting available, player conversation outcome, hostile interruption.
- Ownership: block owns activation/readiness and ambient retirement; scene owns
  its performance. Explicitly restore AI tier, look-at and workspots on exits.
- Evidence: mq010 start 15/2 prepare offscreen; scene 105 ends into scene 23;
  mq003 root h12 activates and waits for spawn before handing off.
- Dependencies: world communities, markers, workspots, crowd areas; these are
  not generated by an abstract conversation node.

**Acceptance:** enter while setup conditions are already satisfied; leave during
ambient speech; return after it ends; interact before an actor is ready; attack.

## 3. Multiple routes to one access commit

**Purpose:** purchase, dialogue/background, skill, or recovered-key routes unlock
the same next stage without duplicate effects.

- Inputs: branch contracts, eligibility predicates, access-state commit,
  obsolete objectives/listeners and one downstream continuation.
- Outputs: access granted with route identity; defer; interruption/failure.
- Ownership: convergence owns access commit and retires unused branches.
  Branch-specific presentation remains local.
- Evidence: mq003 homeless phase hack `suitcase_hacked_out`, shard-use
  `suitcase_unlock_out` and the corresponding device enablement convergence.
- Boundary: purchasing access and unlocking the computer are separate logical
  steps; do not assume the purchase itself emits the device's launch fact.

**Acceptance:** each route independently, key acquired early, two signals close
together, refusal/re-entry and an interrupted losing branch.

## 4. Clue set with bypass and reactions

**Purpose:** inspect evidence in flexible order, with optional scene reactions,
and allow direct discovery to supersede the trail.

- Inputs: clue object list, required set/count policy, event type, per-clue
  reaction entry, result state, bypass condition and journal/mappin bindings.
- Outputs: clue observed, reaction finished, investigation resolved or bypassed.
- Ownership: deduplicate clue completion; retire scan and reaction waits when
  bypassed; explicitly define whether reactions block the final join.
- Evidence: mq003 homeless 113/114 (`Finished`) → scenes 118/119 → AND 120;
  direct corpse discovery 121 → CutControl 122.
- Current gap: ordered `Started` scanning cannot reproduce this contract simply
  by supplying the same clue object list.

**Acceptance:** reverse order, already-scanned clue, discovery before scans,
leave during a reaction, repeat scan and save/load at the join.

## 5. Delayed return

**Purpose:** temporarily close an interaction, communicate waiting, then make
a distinct return entry available.

- Inputs: clock domain/duration, start condition, waiting objective, return
  objective and spatial gate, initial/return scene entries, cancellation.
- Outputs: waiting, return available, resumed interaction or cancelled.
- Ownership: timer owns elapsed time only; composition owns objective and
  scene transition. Separate incidental NPC departure timers.
- Evidence: mq010 Barry phase 22 `knock_on_door_out` → wait objective → 95 →
  three-game-hour node 94 → CutControl 23 → return objective/scene.
- Reuse: compose existing `time_gate`; preserve save-aware state and deliberate
  `IsInside`/`IsOutside` versus crossing-event semantics.

**Acceptance:** wait elsewhere, skip game time, stand at the door, re-enter
before timer completion, cancel during wait, save/load before and after expiry.

## 6. Optional evidence beside the main route

**Purpose:** run an investigation without blocking the main continuation,
while allowing its result to affect later choices.

- Inputs: optional-child start, eligibility, evidence condition, durable
  knowledge fact, commentary contract, parent stop/cancel signal.
- Outputs: knowledge acquired, commentary completed/skipped, branch retired.
- Ownership: evidence and commentary have separate completion states. Ending
  optional commentary must not erase knowledge already acquired.
- Evidence: mq010 root node 3 fans Out1 to nodes 4 and 5; columbarium phase
  9 and 22 both write knowledge despite different optional-conversation states.
- Boundary: a generic entry-time `optional_condition` is insufficient; this
  child lives concurrently with the main route and needs retirement policy.

**Acceptance:** never visit; visit early; observe evidence and leave; finish main
route while investigation runs; cancel/reload while Johnny is active.

## 7. Knowledge-gated report and outcome commit

**Purpose:** distinguish learning evidence from choosing to act on it.

- Inputs: knowledge predicate, choice option, report/decision commit state,
  consequence mappings and optional generic-report fallback.
- Outputs: committed decision; story outcome selected; no decision yet.
- Ownership: scene validates choice eligibility and commits decision; outcome
  orchestration consumes the committed decision independently of scene playback.
- Evidence: mq010 `asked` at Barry n81 → `known` at columbarium 9/22 → police
  n4 option gate → n12 `told` → finale 208/234/241 and outcome scene n18.
- Boundary: avoid exposing a single “good dialogue” boolean that conflates
  conversational score, evidence possession and report choice.

**Acceptance:** know but do not report; generic report without evidence; unlock
option during concurrent work; repeat/interrupt the report; reload after commit.

## 8. Vehicle-delivered encounter

**Purpose:** stage a squad arriving in vehicles before handing it to combat.

- Inputs: vehicle/actor entries, seat mappings, mount readiness, route splines,
  arrival gates, unmount readiness, combat staging and cancellation.
- Outputs: squad staged, combat ready, arrival failed/cancelled.
- Ownership: define who activates/deactivates each community entry and who
  releases AI from vehicle/spline control. Combat counter is a separate block.
- Evidence: mq003 intercept 4/53, assignment and mount branches, truck spline
  nodes 2/14, arrival triggers 79/22, unassignment and `OnUnmount` waits.
- Boundary: neither current combat nor single-vehicle delivery automatically
  supplies the world splines, seats or staged dismount lifecycle.

**Acceptance:** blocked vehicle, missing passenger, early combat/vehicle damage,
player departure, save/load during travel, cancellation while partly dismounted.

## 9. Named-target objective counter

**Purpose:** advance a visible counter once per required target and complete
when the target set is resolved.

- Inputs: explicit target set, defeat semantics, journal counter and result fact.
- Outputs: target resolved, count progress, encounter complete.
- Ownership: set membership and deduplication; handle actors already defeated
  before the watcher starts; do not include incidental community entries.
- Evidence: mq003 intercept h468 has seven independent named conditions,
  counter increments and seven-input AND; outer node 51 writes defeat fact.
- Boundary: source condition class is `CharacterKilled`; nonlethal/default
  semantics require explicit review and an installed test before templating.

**Acceptance:** any target order, repeated events, nonlethal outcomes, a target
defeated during arrival, missing/despawned target, save/load at count N−1.

## 10. World set piece with authoritative gates

**Purpose:** coordinate timed animation, world variants, audio/FX, collision and
gameplay state around an encounter.

- Inputs: named world objects/components, animation, variants, spatial/camera
  gates, duration/fallback, token/prevention scope, encounter signals.
- Outputs: presentation ready/finished, interrupted/abandoned, gameplay available.
- Ownership: restore collision, visibility, audio and prevention state on every
  exit. Avoid making a visual beat the only success signal.
- Evidence: mq003 pod 107/29/104/105 and falling-to-landed swap; separate combat
  fact waits and loot ownership check; mq010 delayed/spatial consequence staging.
- Boundary: heavily world-bound composition, not a universal drop-pod primitive.

**Acceptance:** arrive early/late, look away, leave mid-animation, cancel,
abandonment timeout, reload during object swap and restore the original scope.

## 11. Loot acquisition and completion commit

**Purpose:** distinguish enabling loot, acquiring the target item, closing
commentary and awarding completion/reward.

- Inputs: container, item record, grant/inject policy, authoritative inventory
  condition, encounter gate policy, closing scene and reward/outcome.
- Outputs: loot available, item acquired, quest outcome/reward committed.
- Ownership: one inventory/reward commit; decide early ownership policy and
  prevent repeated grants after interruption or reload.
- Evidence: mq003 pod 96 injects loot; 116 checks quantity; 78/79/75 close the
  retrieval route; 56/66 handle success/reward after the reaction output.
- Boundary: inventory ownership is not shard reading or terminal page viewing.
  This pilot provides no new generic readable-event proof.

**Acceptance:** open container without taking item, acquire item early, full
inventory, repeat interaction, interrupt closing speech, reload after grant.

## 12. Owned scope and deferred cleanup

**Purpose:** restore state acquired by a quest and retire actors/world objects
without changing the committed narrative result.

- Inputs: owned resource/state ledger, terminal outcome, cleanup policy,
  departure/camera gates, optional delay, success/failure distinctions.
- Outputs: outcome committed and cleanup finished as separate signals.
- Ownership: release only the block's acquired content tokens, restrictions,
  tiers, device/variant overrides and spawned entries. Cleanup is idempotent.
- Evidence: mq003 root h163 has two departure branches and a join; homeless
  h1118 uses distance/camera retirement. mq010 normal cleanup waits 12 game
  hours and departure; root failure cleanup has a different policy.
- Boundary: vanilla's `UnblockAll`/`RemoveAllRestrictions` are broad operations;
  preserve their intent through an explicit Ghostline ownership contract.

**Acceptance:** terminal success and failure, player stays nearby, offscreen
retirement, duplicate cleanup, overlapping quests, load after outcome commit but
before cleanup completes.

## Proposed authoring shape

Illustrative design only; this is **not current compiler syntax**:

```yaml
composition: evidence_changes_report
parallel:
  optional_evidence:
    eligible_when: asked_about_contact
    observe: contact_memorial
    produces: knows_contact_truth
    commentary: optional_witness_reaction
    cancel_when: report_resolved
  main_route:
    scene: report_to_contact
    choice:
      requires: knows_contact_truth
      commits: reported_contact_truth
    consequence:
      select_from: reported_contact_truth
      cleanup_policy: after_player_departure
```

The compiler-facing contract would still require concrete scene entries/exits,
NodeRefs, journal paths, item/actor records, clocks, interruption rules and
effect ownership. Narrative aliases should resolve to those bindings rather
than hiding them.

## Promotion order

First strengthen scene-interface validation and owned cleanup contracts, then
exercise a minimal delayed return and knowledge/report composition. Extend clue
investigation to `Finished`/parallel/bypass semantics next. Keep vehicle arrival
and world set pieces as explicitly bound compositions until isolated runtime
tests establish a narrower reusable shape.

Each promoted candidate needs reviewed bindings, cancellation and save/load
behavior, serialization/handle validation, a package verification and an
installed playtest of its own acceptance cases. The existing donor corpus's
proof status is unchanged by this research.
