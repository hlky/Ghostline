# Building navigation

Building Lab generates experimental Human navigation from its room geometry,
door gates and stair flights. It writes native version 8 VAND tile buffers,
embeds a `.navmesh` resource in a registered Navigation sector. An independent
adaptation of upstream Detour loads the buffers and checks actual polygon paths.
This establishes offline format and connectivity evidence. Game loading and
observed NPC traversal remain separate milestones.

## Current evidence

| Check | Result |
| --- | --- |
| Clearance-aware room and partition surfaces | Passing compiler tests |
| Ground room to upper room through guarded stairs | Passing Python graph and Detour path queries |
| Unlocked device doorway | Passing Detour path query through an off-mesh polygon |
| Locked device doorway | Detour refuses the complete route |
| Rotated building over four tiles, including negative coordinates | Passing Detour path query |
| Custom layer 200 to an unmodified vanilla layer 0 tile | Passing Detour query, with each endpoint's layer checked |
| Native CR2W and tile-buffer readback | Passing independent reader checks |
| Archive dependency and payload verification | Verified by the normal WolvenKit packager |
| Cyberpunk loading the tiles and NPC traversal upstairs | Observed in motel-modules on 2026-10-26: 24.05 m in 19.42 s, no detected teleport jumps |
| Door crossing in Cyberpunk | V opens/crosses automatic door; NPC-owned path query between workshop/service returns no path despite both endpoints being found. NPC crossing remains unproven |

The isolated example is
`projects/experiments/building-lab/buildings/navigation-lab.building.json`.
It uses industrial walls, two floors, a guarded stair flight, automatic and
interactive door devices, and layer 200 at anchor `(100, 100, 700)`.
The high platform separates its queries from existing city surfaces. It is a
test location, not a surveyed quest interior.

## Surface construction

`tools/building_navigation.py` unions room footprints, subtracts partition
collision, and erodes the remaining surface by the agent radius. Lintels above
the agent's head do not obstruct the floor. Stair shafts are cut from horizontal
surfaces, and a sloped navigation surface joins their landings. Physical steps
remain solid steps; navigation does not replace collision.

The defaults match the inspected vanilla Human settings: 1.8 m height, 0.3 m
radius and 0.6 m climb. The compiler supports radius 0.2–0.65 m and height
1.2–2.4 m. These settings are not a promise that every NPC body/behaviour uses the
same capability.

The constrained triangulation uses
[Shapely's constrained Delaunay operation](https://shapely.readthedocs.io/en/2.1.2/reference/shapely.constrained_delaunay_triangles.html),
which retains polygon boundary edges. This matters for narrow openings and
stair landing connections. A Python breadth-first query reports surface
connectivity and highlights polygons; it does not simulate game locomotion.

Device doorways introduce a small gap in the ground surface and a Door off-mesh
link between the two sides. A locked door's native off-mesh polygon starts with
zero traversal flags. The door's `AIOffMeshConnectionComponent` refers to the
same uniquely named world connection as the tile metadata. Cross-node references
are registered as absolute paths (`$/03_night_city/#building_...`) in the
sector NodeRef table. A bare `#alias` does not register itself; hashing it as
though it were an absolute path produces an unusable identity. See the local
[NodeRef registration reference](../../modding_docs/for-mod-creators-theory/files-and-what-they-do/file-formats/the-whole-world-.streamingsector/noderefs.md). `DoorControllerPS`
settings are serialized in an instance package with verified component CRUIDs.
A separate `.devices` resource is registered into the vanilla device registry.
Live unlock/relock and automatic-close behaviour still need confirmation.

## Native layout

The writer follows the inspected vanilla buffers and WolvenKit's `TilesReader`,
with the field interpretation cross-checked against
[Detour's header](https://github.com/recastnavigation/recastnavigation/blob/main/Detour/Include/DetourNavMesh.h)
and [mesh builder](https://github.com/recastnavigation/recastnavigation/blob/main/Detour/Source/DetourNavMeshBuilder.cpp).
The correspondence is an implementation inference, independently exercised by
loading the generated bytes; it is not official CDPR authoring documentation.

| Element | Building Lab encoding |
| --- | --- |
| Tile coordinates | Vanilla Human grid, 32.4 m per tile |
| Header | `VAND`, version 8, 100 bytes including agent/bounds fields |
| Polygon | Three vertex slots, three neighbour slots, 20 bytes |
| Interior adjacency | Neighbour polygon index plus one; zero is a boundary |
| External adjacency | `0x8000` portal bit plus Detour side code |
| Links | Reserved 16-byte runtime link records |
| Detail mesh | One detail triangle per ground polygon, no added detail vertices |
| BV tree | Quantized polygon bounds, preorder branches with negative escape offsets, 2N slots including final padding |
| Off-mesh connection | 40 bytes, including a 64-bit user ID |
| Agent | Human |
| Position components | VAND X/Z/Y; RED world X/Y/Z elsewhere |

Geometry is clipped at tile boundaries and interpolates stair height. Polygon
orientation, reciprocal adjacency, external portals, signed tile coordinates,
off-mesh metadata and raw-buffer byte preservation have regression coverage.
The navigation node's placement controls its spatial registration; vertices
already contain baked world coordinates and are not translated a second time.

## Existing city navigation

Additive exports require a nonzero tile layer so they do not reuse vanilla
layer-zero tile identities. A separate layer is not a world-navmesh rebuild.
It does not carve out existing polygons beneath new walls or join surfaces
merely because they are nearby.

Author entrance connections in `layout.navigation.connections`, or use **Add
entrance link** in the editor's route dialog:

```json
{
  "id": "street",
  "from": [4.5, 1.5, 0],
  "to": [4.5, -1.0, 0]
}
```

Coordinates are local to the building. The source must lie on its generated
surface. The target can lie on surveyed existing Human coverage. Links are
bidirectional Floor connections, limited to 4 m in total and
0.6 m vertically. They do not create a physical floor or clear a facade.
Use a doorway/entrance patch and a walkable approach at the same location.

The coexistence oracle loads a real, unchanged tile from the first Human
resource embedded in `navigation_1_-7_0_3.streamingsector`. It loads a small
generated room on layer 200 and follows a Floor connection to layer 0. The
oracle reports the selected endpoint layers and height errors, so selecting
only an underlying vanilla polygon cannot count as success. Removing the
connection is a required negative control. This remains an offline test.

For a real retrofit, survey the exact floor elevation and approach, check both
entrance directions, and verify surrounding NPC routes after changing walls.
Whole-city generation, automatic vanilla tile merging and crowd/traffic
navigation are not implemented.

Package receipts, the 872-test result and the remaining live-test matrix are
recorded in [`reference/world/building-lab-verification.json`](../../reference/world/building-lab-verification.json).

Checked results, hashes and upstream provenance are recorded in
[`reference/world/building-navigation-proof.json`](../../reference/world/building-navigation-proof.json).

WolvenKit skips standalone `.navmesh` files during packing. The exporter follows
vanilla by embedding the Human resource inside the Navigation sector, with matching
`Embedded` imports and `localInplaceResource`. Package dependency checks consult
the binary embedded table, so a raw declaration alone cannot hide a missing file.

## Reproduce the independent oracle

The oracle is optional and requires clang++ and a local official Recast checkout.
It copies sources into generated output; it does not edit the checkout.

```powershell
git clone --depth 1 https://github.com/recastnavigation/recastnavigation.git .tmp/building-nav-oracle/recastnavigation
uv run python -B tools/building_nav_oracle.py projects/experiments/building-lab/buildings/navigation-lab.building.json --recast-source .tmp/building-nav-oracle/recastnavigation --start 1.5 1.5 0 --end 1.5 1.5 4.4
```

The build receipt records the exact upstream commit, executable hash and these
adaptations: three-vertex polygons, tile version 8, 64-bit polygon references
and 64-bit off-mesh user IDs. The initial checkout was
`9f4ce64458dfae86e1239c525ddc219c4e9e06f1`. Upstream's unmodified version-7
writer is not a drop-in Cyberpunk generator.

`--extra-tile <file.vand>` co-loads raw reference buffers for integration queries.
Never mark a whole game route proven solely from this oracle.

## Native game and NPC proof

Export the example and build its diagnostic profile:

```powershell
uv run python -B tools/building_builder.py export projects/experiments/building-lab/buildings/navigation-lab.building.json --out projects/experiments/building-lab/generated/playtest --serialize
uv run python -B tools/package_project.py --project projects/experiments/building-lab/generated/playtest --profile building-lab-test
```

The default `building-lab` profile excludes diagnostic loose files. The
`building-lab-test` profile selects a CET mod and a generated `contract.json`
with walkable room and stair sample points. Do not substitute a full GUI source
copy for profile-aware packaging when preparing a release.

Use a dedicated manual test save predating Building Lab installation. No quest
facts or story prerequisites are required. After installing the candidate,
restart the game and load that save. Open the CET overlay and the Building Lab
runtime window. **Teleport V to start** holds V above the start briefly while
navigation streams, then releases the player when the native point query finds
the floor. A timeout returns V to the prior position.

Run **native query** between two selected points. It invokes the game's
`AINavigationSystem.CalculatePathForCharacter` and rejects partial/snapped
paths whose first or last point misses the requested position. Its report
distinguishes player and NPC query owners. A secondary `AINavigationSystem.StartPathfinding` /
`GetResult` query records the AI query result independently, polling for up to
three seconds. It does not overwrite the direct endpoint-path pass flag. Door
diagnostics include resolved connection IDs and component reference bindings.

For actual movement, bind a disposable looked-at human NPC or spawn a generic
NPC using a verified existing Character record. Spawning requires Codeware;
the harness intentionally has no unverified default record. Bring the NPC to
the start, then choose **Walk NPC to end**. The command explicitly sets
`ignoreNavigation=false`. A complete native path and valid endpoint samples are required before sending
the movement command. A diagnostic failed-path attempt caused a 7.57 m jump
in 0.11 s in game; the guard rejects that as traversal failure. The AI
controller decides the route; no direct movement or door-link flag override
is used. Reports retain `native_query_passed` independently of
`npc_movement_passed`, and record door PS state/component availability.
The observer records positions, elapsed time,
travelled distance, arrival and teleport-sized jumps. A successful query alone
cannot set `npc_movement_passed`.

Repeat through the shared doorway, up and down the stairs, with locked/unlocked
doors, after leaving and returning, and after save/load. Test player collision,
shaft guards, headroom and streaming separately. Use **Stop and restore /
despawn test NPC** and **Return V** before normal play. The harness writes
`runtime-report.json` in its installed CET directory. Lua syntax verification
does not establish that these live bindings ran successfully.

Once those observations pass for a named package hash and save, the runtime
status can be advanced from experimental. Until then, use stationary quest
actors or known vanilla navigation for production scenes needing reliable AI.


## Retrofitting a surveyed entrance

`navigation.door_connections` can give a device edge explicit local `from` and
`to` endpoints, within 4 m and 0.6 m vertically. They must straddle the door
plane and cross its centred aperture. The compiler orders the inside endpoint
first so the owning tile can attach the link; a surveyed street surface may
supply the other endpoint. `navigation.test_points` prepends named local
positions to the CET controls, including explicit outside starting points.

A room can supply `ceiling_height` between 2.4 m and its kit's wall height to
keep a new lining below a retained shell roof. This does not lower the wall
mesh or the physical door aperture. Ordinary entrance links use Regular area
3 and a Floor node; Jump area 12 is a different traversal type.

The Rancho example has retained layer-0 navigation inside the shell as well as
outside it. A short Floor link joins that retained interior surface to the
new layer. Test both load orders/destination layer selections in the offline
oracle: otherwise a route can appear to fail merely because the nearest query
selected a different overlapping interior surface. The game still needs direct
endpoint queries and observed walks through the specific entrance.


### Native door presets and existing apertures

`door_devices` maps a device edge to a measured `preset` (`sliding_entropy_c`
or `hinged_h`), optional `yaw_offset` (0 or 180), and local XYZ `offset`
(each within ±0.5 m). The preset selects the native template and appearance
and supplies the hinge-to-casing-centre distance. Door navigation endpoints
remain aligned to the wall aperture independently of the device's facing.
`hinged_h` uses a 2.5 m collision aperture and has been measured against the
Rancho door bay; check another kit's visual opening before using this taller
leaf. The preview remains schematic.

The active Rancho revision replaces the existing white static door on the long
façade with the matching native hinged device. Its side wall and generator are
restored. The old fake leaf/casing are static placements 419/398 in
`exterior_-11_-23_0_0`; replacement collision targets actor 17 of placement 1377
in `exterior_-6_-12_0_1` and actor 124 of placement 856 in
`exterior_-2_-3_0_3`. The original brick door-bay mesh is retained. See
`projects/experiments/building-lab/surveys/rancho-original-door.json` for poses,
pinned source selection, leaf bounds, stock inward swing and eight offline
navigation controls. Runtime verification is separate.

The original fake white leaf also has a separate fixed collision box at
placement 850, actor 123, shape 0 in `exterior_-2_-3_0_3`. It spans the entire
opening and must be removed along with the static leaf. Actor-pivot matching
of just the casing/door-bay resources missed this independent blocker; inspect
primitive bounds over the complete entrance corridor after moving an entrance.


## Surveyed external surfaces and terrain replacement

`navigation.surfaces` accepts up to 128 explicit local XYZ triangles, with
nonzero projected area and slopes no steeper than 35 degrees. These describe
retained physical surfaces, not generated geometry. Rancho residential uses
four triangles over its existing porch/steps. Do not add a walk surface without
matching retained or generated collision.

`navigation.terrain_mask` pins a complete serialized vanilla navigation sector,
resource index, placement index, shell outline and local height range. Export
copies the selected Human resource, clearing only polygon flag bytes for
triangles completely inside the buffered shell footprint and height range.
It preserves every other byte, all buffers, original tile coordinates, topology,
metadata and off-mesh identities. Special polygons and boundary-crossing
triangles stay. Export creates a mod-owned embedded resource/sector with a
streaming descriptor covering the complete retained resource, then ArchiveXL
replaces its original navigation node. The original node deletion is only
accepted with the matching pinned replacement contract.

This addresses nearest-surface ties against terrain under a retrofit. The
Rancho residential example initially selected lower/overlapping ground for
three room destinations; a bridge alone would not prevent routes bypassing
the locked front door. Its final expansion-based mask disables 43 polygons
inside the actual shell, preserving 25 Human tile buffers and Vehicle resources.
All eight room targets then pass street↔room route controls in either tile
load order and fail when the entrance is locked. These are offline checks;
streaming registration and physical NPC traversal need an in-game test.

Decorative door replacement accepts only the pinned vanilla
`single_door_decorative.ent`; entity proxies require their exact owner hash.
Generic NPC/gameplay entities are not removable through this narrow contract.
`room_lighting: true` adds one warm vanilla point light near each room's ceiling.
Native readback verifies light colour, intensity, radius and streaming distance.


Instanced shell occluders require a separate survey from mesh/collision pivots.
Their placement can be at world zero while the appendix stores world-space
matrices. For the supported short appendix, the first byte is the matrix count
and each following matrix contains sixteen little-endian floats. ArchiveXL
1.27 removes the entire `worldInstancedOccluderNode`; it does not implement
`instanceDeletions` for that class. The retrofit validator therefore requires
`expectedInstances` and `removeWholeGroup: true`, rejects partial instance
selections, and still pins the source SHA, placement type and node count.
Only select a whole group after reviewing every matrix against the target
building. The Rancho residential audit documents three house-only groups
across detail levels; adjacent-house groups stay in place.

Shared wall door casings are centred across `kit.wall_thickness`, rather than
anchored on the first facing. Exterior retrofits retain their surveyed facade
alignment and use an explicit device offset when necessary. Door connection
endpoints remain centred on the aperture; shifting casing depth does not
change walkable navigation surfaces.


Layouts may specify a surveyed `storey_height` (3–6 m) independently of the
kit default. Compact stair positions, widths and runs use a 5 cm grid;
minimum width is 1.2 m, minimum landing 1.2 m, default landing 3 m. Both the
entire flight and landings must fit inside one authored room on each floor.
Slabs are split around exact shaft/guard rectangles instead of deleting a
whole tile; the walkable ramp must still attach to both floor polygons.

Rancho `plain_door_surrounds` builds jambs/header from measured full-wall
sections, preserving the door root and aperture while avoiding recessed
exterior trim. An exterior `window` opening requires a `windows` entry with
width/sill/height; it changes visual lining only and retains blocking wall
collision. Library modules support positive XYZ scale; scaled bounds feed
anchor, preview, streaming extent and optional box collision. The measured
Rancho window alone accepts `clear_glass`; export includes the mod-owned
mesh with its external clear-glass material, native readback and geometry
buffer check. Vanilla parallax windows are not assumed to be transparent.

## Measured house infills and open door leaves

The residential access revision follows the original shell's three ground
access points and wraparound balcony. `shell_rooms` describe bounded,
non-grid rectangular annexes with surveyed floor elevations; `shell_liners`
fit off-centre apertures, and `shell_doors` supply native devices with explicit
gates/endpoints. They use the Rancho measured mesh contract. A garage may use
a lower floor and `shell_steps` for a real physical rise into the house.
`shell_plinths` seal the gap beneath higher main-house wall bases. No teleport
is used between annexes, rooms or balcony.

The stock hinged_h open leaf is measured at its +90-degree pose and removed
from walkable polygons before agent-radius erosion. This also applies to
shell step landings; an otherwise clear door link can still lead onto a
corner-cutting landing. Device links remain gated separately. This reserves
a static fully-open pose; live door animation and NPC steering still require
observation. It is not a general dynamic obstacle system.

`stairs[].reverse` reverses riser/ramp heights, runtime foot/top probes and the
low-end guard closure together. `fit_walls_to_storeys` clips Rancho wall caps
below upper slabs and removes buried foundation geometry from upper walls.
Floor meshes normalize their full 3.005 m native bounds, including lips,
so adjoining tiles and shaft cuts do not have overlapping top faces.

Retained balcony navigation comes from surveyed native floor envelopes,
eroded by the same 0.3 m agent radius. Clutter removals pin individual source
placements and collision shapes. The barrel keepout is approximate and needs
a live clearance check. The rear porch also requires masking the vanilla
Human polygons beneath it: face 105 sat 0.17 m above the intended porch and
made results depend on tile load order. The revised local mask disables 51
polygons, preserving all 25 buffers and changing only polygon flag bytes.
See `projects/experiments/building-lab/surveys/rancho-residential-house-access.json`
for source pins, layout measurements, screenshot hashes and playtest checks.


`stairs[].type = "return"` generates two parallel flights with a central
partition and a half-storey turning landing. `width` covers both flights and
a 15–40 cm centre; `flight_width` is at least 1.2 m. Each run is at least 3 m
and each flight's slope remains at most 35 degrees. Physical risers, shared
turn, clearance-eroded ramps, probes and shaft cuts follow this form together.
The low-flight end guard cuts only its half of the upper floor; a full-width
12 cm guard overcut would leave unsupported navigation at the upper exit.

Measured shell devices may retain surveyed positive XYZ `scale`. Native
placement scale is round-tripped alongside positions and identities. The
w300_h250 garage preset uses its own DoorController CRUID, not the generic
single-door controller. Its original static frame and fixed collision must
be removed when the moving device supplies its own assembly. Always measure
source placement scale before sizing a lining aperture from a mesh's name.


Straight flights accept `axis: "x"` for a +X run, with width extending toward
-Y. Geometry, floor/ceiling cuts, route ramps and probes share that coordinate
frame. A `wall_side` omits the guard where an adjacent wall already encloses
the flight. `enclosed` replaces rising ground guards with authored wall liners;
upper shaft guards remain. Measured `shell_steps` use the same axis convention.
Both bottom and top step ports must constrain adjacent floor triangulation.

A shell room may include adjacent rectangular `extensions`; these share one
clearance-eroded navigation footprint, preserving a notch without an artificial
internal seam. Liners author their outer walls. The expanded garage and living
annex use this to follow the user's revised plan.

For the residential garage, entity placement scale was insufficient in game.
Scale the rigid frame component, the animated panel's skeleton root and the
player blocker consistently. The mod-owned `rancho-garage.rig` retains all bone
identities, parent indices, translations and rotations; only root scale changes.
Do not assign `visualScale` to an `entPhysicalSkinnedMeshComponent`: WolvenKit
rejects that nonexistent property. Check native resource readback and then test
the actual animation/collision in game.
